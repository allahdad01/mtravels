DATABASE SCHEMA
================================================================================

TABLES CREATED:
1. chat_audit_log (main audit trail)
   - 13 columns with detailed context
   - 6 optimized indexes for fast queries
   - Foreign keys for data integrity

2. chat_audit_log_archive (historical data)
   - Same structure for archiving old logs
   - Extra archived_at timestamp

EVENTS TRACKED:
- send_message (with size, encryption status, key ID)
- read_message (timestamp, user)
- block_user / unblock_user (user, target, time)
- mute_user / unmute_user (user, target, time)
- encrypt_message / decrypt_message (algorithm, key ID)
- access_denied (reason, user, time)
- settings_change (setting, old value, new value)

STATUS VALUES:
- success (operation completed)
- denied (access denied)
- failed (operation failed)
- error (system error)

TROUBLESHOOTING
================================================================================

Q: I'm seeing errors when I access admin/audit_logs.php
A: You need to apply the database migration first.
   Go to: http://localhost/mtravels/apply_migration_004.php

Q: The test script shows errors
A: Check that the migration was applied successfully.
   Run: http://localhost/mtravels/apply_migration_004.php

Q: Logs aren't appearing after I send a message
A: 1. Verify tables exist in database
   2. Check that ChatAudit was imported in API files
   3. Send a fresh message
   4. Check database directly: SELECT * FROM chat_audit_log;

Q: What if the migration fails?
A: 1. Check database credentials
   2. Ensure user has CREATE TABLE permission
   3. Try applying via phpMyAdmin manually
   4. Check MySQL error logs

Q: How do I clean old logs?
A: ChatAudit::archiveOldLogs($tenantId, 90);
   This deletes logs older than 90 days.
